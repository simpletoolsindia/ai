## 1. Project Overview

### What is ai?

`ai` is a fork of the upstream **`pi`** self-extensible coding agent (https://github.com/earendil-works/pi), repackaged and renamed under the `@simpletoolsindiaorg` npm scope. The fork preserves the original architecture, agent loop, TUI, extension system, and provider implementations — only the identity and a small number of branding strings were changed.

The product is a terminal-based interactive coding agent that:
- Reads files, runs bash, edits code, writes new files
- Supports multiple LLM providers (OpenAI, Anthropic, Google, Bedrock, OpenRouter, Ollama, etc.)
- Streams responses, supports parallel/queued messages, model cycling, thinking-level control
- Manages sessions on disk as JSONL; can resume, fork, branch, export, and share
- Extensible via TypeScript extensions, skills (markdown), prompt templates, and themes
- Has a self-update mechanism (`ai update self`) and a private plugin store

### Fork context

| | Upstream `pi` | This fork `ai` |
|---|---|---|
| Repo | `github.com/earendil-works/pi` | `github.com/simpletoolsindiaorg/ai` |
| Scope | `@earendil-works/pi-*` | `@simpletoolsindiaorg/ai-*` |
| Bin | `pi` | `ai` |
| User config dir | `~/.pi/agent/` | `~/.ai/agent/` |
| Project config dir | `.pi/` | `.ai/` |
| License | MIT (Copyright Mario Zechner) | MIT (inherits upstream, see [LICENSE](LICENSE) and [NOTICE.md](NOTICE.md)) |

**Most changes should go upstream first.** If you find a bug in the agent loop, a tool, a provider, the TUI, or the extension system, the right place to fix it is the upstream [pi](https://github.com/earendil-works/pi) repository. After the upstream fix lands, this fork can be rebased onto it.

See [CONTRIBUTING.md](CONTRIBUTING.md) for the policy on what belongs in the fork vs. upstream.

### Why this is a fork, not a rename

- The `@earendil-works` npm scope and the `pi` name are the upstream maintainer's identity.
- The maintainer (Mario Zechner) made deliberate design choices around the `pi` name and `π` symbol.
- A clean rename of an active OSS project without the maintainer's involvement would be a misleading impersonation.
- The fork preserves attribution (LICENSE, NOTICE.md), provides back-compat for `piConfig`/`pkg.pi`/`@mariozechner/pi-*` aliases, and clearly identifies itself as a fork at every user-facing surface.

## 3. Architecture Details

The four packages form a strict bottom-up dependency graph. Lower packages never import from higher ones.

```
        ┌─────────────────────────────────────────┐
        │  @simpletoolsindiaorg/ai-coding-agent   │   ← CLI, TUI mode, tools
        │  (the `ai` binary at dist/cli.js)       │
        └────────────────────┬────────────────────┘
                             │
        ┌────────────────────┴────────────────────┐
        │  @simpletoolsindiaorg/ai-agent          │   ← Agent runtime
        │  (agent loop, state, tool orchestration)│
        └────────────────────┬────────────────────┘
                             │
              ┌──────────────┴──────────────┐
              │                             │
   ┌──────────▼──────────┐    ┌──────────────▼────────────┐
   │  @simpletoolsindiaorg/  │    │  @simpletoolsindiaorg/  │
   │  ai-tui                │    │  ai-provider             │
   │  (Container, Text,    │    │  (streamSimple, Model,   │
   │  Markdown, Image,     │    │   OpenAI/Anthropic/etc)  │
   │  dynamic diffing)     │    │                          │
   └───────────────────────┘    └──────────────────────────┘
```

### 3.1 `@simpletoolsindiaorg/ai-provider` (LLM layer)

`packages/ai/src/`

- **`types.ts`** — `Model`, `Message`, `Api`, `ThinkingLevel`, transport types
- **`providers/`** — one file per provider (`openai-completions.ts`, `anthropic.ts`, `google.ts`, `bedrock.ts`, `azure-openai-responses.ts`, `openai-codex-responses.ts`, `faux.ts`, `mistral.ts`, `nvidia-nim.ts`, `cloudflare-ai-gateway.ts`, etc.)
- **`utils/oauth/`** — OAuth flows for subscription providers (OpenAI Codex, Anthropic, GitHub Copilot, Google)
- **`utils/`** — shared helpers (provider config, env keys, model conversion)
- **`stream.ts`** — `streamSimple()`, the unified streaming entry point
- **`models.generated.ts`** — auto-generated list of well-known models; **never edit directly** — edit `scripts/generate-models.ts` and regenerate

The provider layer is the only place that talks to LLM APIs. The unified `streamSimple(model, context, options)` returns an `AsyncIterable` of normalized events. Every provider implementation must conform to this shape.

### 3.2 `@simpletoolsindiaorg/ai-agent` (Agent runtime)

`packages/agent/src/`

- **`agent.ts`** — `Agent` class: state management, model state, tool registry, thinking-level
- **`agent-loop.ts`** — `runAgentLoop()`, `runAgentLoopContinue()`: the core turn loop. Sends a request, streams the response, executes tool calls, feeds results back, repeats until the model stops
- **`types.ts`** — `AgentTool`, `AgentState`, `AgentMessage`, `AgentContext`, `AgentEvent`, lifecycle hook types
- **`proxy.ts`** — proxy/transparent model wrapper for the third-party "opencode" provider
- **`harness/`** — re-exports, prompt templates, session types, utils, env, system prompt
- **`index.ts`** — public surface

The agent runtime is **transport-agnostic** — it doesn't know about TUI, sessions, or extensions. It takes a model, system prompt, messages, and tools, and produces a sequence of events.

### 3.3 `@simpletoolsindiaorg/ai-tui` (Terminal UI)

`packages/tui/src/`

- **`tui.ts`** — the TUI engine: `TUI` class manages root container, focus, event loop, rendering
- **`components/`** — `Container`, `Text`, `Markdown`, `Image`, `Spacer`, `BorderedLoader`, `SelectList`, `DynamicBorder`, `KeybindingHints`, etc.
- **Differential rendering** — the TUI re-renders only what changed, frame-by-frame, with cursor save/restore
- **Keyboard handling** — `Key`, `KeyId`, `parseKey`, app keybindings (`DEFAULT_APP_KEYBINDINGS` in `tui/src/tui.ts`)

The TUI is **framework-free** (no React/Ink). Components are plain TS classes with `render(width): string[]` methods. The engine diffs line-by-line to avoid flicker.

### 3.5 Extension model

Extensions are TypeScript files that export a default function. The loader:

1. **Discovers** them from `~/.ai/agent/extensions/` (user) and `.ai/extensions/` (project), plus package manifests with `ai.extensions` (back-compat: `pi.extensions`)
2. **Resolves** dependencies via `npm`/`pnpm`/`bun` (managed by `package-manager.ts`)
3. **Loads** with `jiti` (in Node) or virtual modules (in Bun binary) — both work because the bundled module map aliases `@simpletoolsindiaorg/ai-*` AND `@mariozechner/pi-*` to the same internal modules
4. **Runs** them in the same process with an `ExtensionAPI` object: `pi.registerTool(...)`, `pi.registerCommand(...)`, `pi.registerProvider(...)`, `pi.registerShellCommand(...)`, `pi.registerEvent(...)`, `pi.on("event", handler)`, `pi.sendMessage(...)`, etc. (Note: the parameter name in the example extensions is `ai` after the fork; `pi` works via back-compat aliasing)

### 3.6 Session lifecycle

```
[start] → [load session JSONL or new] → [register extensions] → [register tools] → 
[show welcome screen] → [user types prompt] → 
[agent loop: stream → tool calls → results → repeat until stop] →
[persist messages to JSONL] → [show response] → [next prompt]
```

On startup:
1. Parse CLI args (`cli/args.ts`)
2. Init `config.ts` (load `~/.ai/agent/models.json`, `settings.json`, `auth.json`, `trust.json`, project `.ai/`)
3. Resolve model (CLI arg → `AI_DEFAULT_MODEL` env → settings → first available)
4. Init `AgentSessionRuntime`
5. If `--print` or `-p` → `print-mode.ts`; if `--rpc` → `rpc-mode.ts`; else → `interactive-mode.ts` (TUI)
6. Load extensions (via `extensions/loader.ts`)
7. Show startup notices (changelog if new version, earendil announcement, loaded resources, keybinding hints)
8. Enter main loop

## 4. Build & Runtime

### Prerequisites

- Node.js >= 22.19.0 (see root `package.json` `engines.node`)
- npm 10+
- (optional) Bun for binary builds and 2× faster extension loading
- (optional) `rg` and `fd` are auto-downloaded on first run if missing

### Common commands

From the repo root:

```bash
npm install --ignore-scripts    # Install all deps without lifecycle scripts
npm run build                   # Build tui → ai-provider → ai-agent → ai-coding-agent
npm run check                   # Lint + format + typecheck + supply-chain checks
./test.sh                       # Run all non-e2e tests
./ai-test.sh                    # Run the ai CLI from sources (uses tsx)
```

### Per-package commands

Each package supports:

```bash
cd packages/<name>
npm run build                   # Build this package
npm test                        # Run this package's vitest suite
npm run clean                   # Remove dist/
```

### Build order

The `npm run build` script at the root enforces: `tui` → `ai-provider` → `ai-agent` → `ai-coding-agent`. The coding-agent CLI (`dist/cli.js`) is the final binary and is what `ai-test.sh` invokes.

### Running from sources (no build needed)

`./ai-test.sh` uses `tsx` to run `packages/coding-agent/src/cli.ts` directly. Useful for fast iteration.

### Running a specific test

```bash
cd packages/coding-agent
node ../../node_modules/vitest/dist/cli.js --run test/specific.test.ts
```

## 5. Naming & Identity Conventions

These rules are **fork-specific**. They preserve the upstream's design and add the fork's identity on top.

### 5.1 Back-compat strategy

Everywhere upstream used the `pi` identity, the fork accepts **both** the new and old names:

| New (fork) | Old (upstream, still accepted) | Where |
|---|---|---|
| `aiConfig` in `package.json` | `piConfig` (still read) | `core/extensions/loader.ts`, `core/package-manager.ts` |
| `ai.extensions` etc. in extension manifests | `pi.extensions` (still read) | same |
| `AI_OFFLINE` env var | `PI_OFFLINE` (still read) | `core/settings-manager.ts`, etc. |
| `AI_TELEMETRY` | `PI_TELEMETRY` | `core/telemetry.ts` |
| `AI_SHARE_VIEWER_URL` | `PI_SHARE_VIEWER_URL` | `core/config.ts` |
| `AI_CLEAR_ON_SHRINK` | `PI_CLEAR_ON_SHRINK` | `core/settings-manager.ts` |
| `AI_HARDWARE_CURSOR` | `PI_HARDWARE_CURSOR` | `core/settings-manager.ts` |
| `AI_CODING_AGENT_DIR` | `PI_CODING_AGENT_DIR` | `cli.ts`, `core/config.ts` |
| `AI_SKIP_VERSION_CHECK` | (none — fork only) | `utils/version-check.ts` |
| `SkillDiscoveryMode: "ai"` | `"pi"` (still read) | `core/package-manager.ts` |
| `update ai` subcommand | `update pi` (still accepted) | `package-manager-cli.ts` |
| `@simpletoolsindiaorg/ai-*` imports | `@mariozechner/pi-*` (alias) | `core/extensions/loader.ts` |

**When adding new code or new config keys, use the new `ai` names. Don't add new `pi` aliases — those are only for compatibility with existing extensions and configs.**

### 5.2 Branding rules

- CLI binary name: `ai` (not `pi`)
- App title: `α` (alpha) — used in TUI title bar, package registry symbol keys, etc.
- Config dir: `.ai` (user) and `.ai/` (project)
- `models.json` location: `~/.ai/agent/models.json`
- HTTP user agent: `ai/<version> (...)`
- OpenRouter `X-OpenRouter-Title`: `ai`
- OpenRouter `HTTP-Referer`: `https://github.com/simpletoolsindiaorg/ai` (placeholder — change when the fork has a real homepage)

## 6. Development Rules

### 6.1 Conversational style

- Keep answers short and concise
- No emojis in commits, issues, PR comments, or code
- No fluff or cheerful filler text (e.g. "Thanks @user" not "Thanks so much @user!")
- Technical prose only, be direct
- When the user asks a question, answer it first before making edits or running implementation commands.
- When responding to user feedback or an analysis, explicitly say whether you agree or disagree before saying what you changed.

### 6.2 Code quality

- Read files in full before wide-ranging changes, before editing files you have not fully inspected, and when asked to investigate or audit. Do not rely on search snippets for broad changes.
- No `any` unless absolutely necessary.
- Inline single-line helpers that have only one call site.
- Check node_modules for external API types; don't guess.
- **No inline imports** (`await import()`, `import("pkg").Type`, dynamic type imports). Top-level imports only.
- Never remove or downgrade code to fix type errors from outdated deps; upgrade the dep instead.
- Use only erasable TypeScript syntax (Node strip-only mode) in code checked by the root config (`packages/*/src`, `packages/*/test`, `packages/coding-agent/examples`): no parameter properties, `enum`, `namespace`/`module`, `import =`, `export =`, or other constructs needing JS emit. Use explicit fields with constructor assignments.
- Always ask before removing functionality or code that appears intentional.
- Do not preserve backward compatibility unless the user asks for it. (Note: the `pi` → `ai` rename **does** preserve back-compat, see §5.1.)
- Never hardcode key checks (e.g. `matchesKey(keyData, "ctrl+x")`). Add defaults to `DEFAULT_EDITOR_KEYBINDINGS` or `DEFAULT_APP_KEYBINDINGS` so they stay configurable.
- Never modify `packages/ai/src/models.generated.ts` directly; update `packages/ai/scripts/generate-models.ts` instead, then regenerate. Including the resulting `models.generated.ts` diff is always OK, even if regeneration includes unrelated upstream model metadata changes.

### 6.3 Commands

- After code changes (not docs): `npm run check` (full output, no tail). Fix all errors, warnings, and infos before committing. Does not run tests.
- Never run `npm run build` or `npm test` unless requested by the user.
- Never run the full vitest suite directly: it includes e2e tests that activate when endpoint/auth env vars are present. For all non-e2e tests, run `./test.sh` from the repo root. Otherwise run specific tests from the package root: `node ../../node_modules/vitest/dist/cli.js --run test/specific.test.ts`.
- If you create or modify a test file, run it and iterate on test or implementation until it passes.
- For `packages/coding-agent/test/suite/`, use `test/suite/harness.ts` + the faux provider. No real provider APIs, keys, or paid tokens.
- Put issue-specific regressions under `packages/coding-agent/test/suite/regressions/` named `<issue-number>-<short-slug>.test.ts`.
- For ad-hoc scripts, `write` them to a temp file (e.g. `/tmp`), run, edit if needed, remove when done. Don't embed multi-line scripts in `bash` commands.
- Never commit unless the user asks.

### 6.4 Dependency and install security

- Treat npm dep and lockfile changes as reviewed code. Direct external deps stay pinned to exact versions.
- Hydrate/update locally with `npm install --ignore-scripts`; clean/CI-style with `npm ci --ignore-scripts`. Don't run lifecycle scripts unless the user asks.
- If dep metadata changes, refresh `package-lock.json` with `npm install --package-lock-only --ignore-scripts`.
- If `packages/coding-agent/npm-shrinkwrap.json` needs regen, run `node scripts/generate-coding-agent-shrinkwrap.mjs` (verify with `--check` or `npm run check`). New deps with lifecycle scripts require review and an explicit allowlist entry in that script; never add one silently.
- Pre-commit blocks lockfile commits unless `PI_ALLOW_LOCKFILE_CHANGE=1` (yes, the env var is still `PI_` for back-compat with upstream's tooling). Don't bypass unless the user wants the lockfile change committed.

### 6.5 Git

Multiple ai sessions may be running in this cwd at the same time, each modifying different files. Git operations that touch unstaged, staged, or untracked files outside your own changes will stomp on other sessions' work. Follow these rules:

Committing:

- Only commit files YOU changed in THIS session.
- Stage explicit paths (`git add <path1> <path2>`); never `git add -A` / `git add .`.
- Before committing, run `git status` and verify you are only staging your files.
- `packages/ai/src/models.generated.ts` may always be included alongside your files.
- Message format: `{feat,fix,docs}[(ai,tui,agent,coding-agent)]: <commit message> (optionally multiple lines)`. Message is informative and concise.

Never run (destroys other agents' work or bypasses checks):

- `git reset --hard`, `git checkout .`, `git clean -fd`, `git stash`, `git add -A`, `git add .`, `git commit --no-verify`.

If rebase conflicts occur:

- Resolve conflicts only in files you modified.
- If a conflict is in a file you did not modify, abort and ask the user.
- Never force push.

### 6.6 Issues and PRs

See [CONTRIBUTING.md](CONTRIBUTING.md) for the contributor gate (auto-close workflows, `lgtm`/`lgtmi`, quality bar).

When reviewing PRs:

- Do not run `gh pr checkout`, `git switch`, or otherwise move the worktree to the PR branch unless the user explicitly asks.
- Use `gh pr view`, `gh pr diff`, `gh api`, and local `git show`/`git diff` against fetched refs to inspect PR metadata, commits, and patches without changing branches.
- If you need PR file contents, fetch/read them into temporary files or use `git show <ref>:<path>` without switching branches.

When creating issues:

- Add `pkg:*` labels for affected packages (`pkg:agent`, `pkg:ai`, `pkg:coding-agent`, `pkg:tui`); use all that apply.

When posting issue/PR comments:

- Write the comment to a temp file and post with `gh issue/pr comment --body-file` (never multi-line markdown via `--body`).
- Keep comments concise, technical, in the user's tone.
- End every AI-posted comment with the AI-generated disclaimer line specified by the originating prompt (e.g. `This comment is AI-generated by `/wr``).

When closing issues via commit:

- Include `fixes #<number>` or `closes #<number>` in the message so merging auto-closes the issue. For multiple issues, repeat the keyword per issue (`closes #1, closes #2`); a shared keyword (`closes #1, #2`) only closes the first.

## 7. Release & Publishing

### 7.1 Versioning

**Lockstep versioning**: all four packages share one version; every release updates all together. `patch` = fixes + additions, `minor` = breaking changes. No major releases (no `1.0.0` ever — the project uses `0.x.y`).

The first fork release is `0.79.0` (next after upstream's last `0.78.1`).

### 7.2 Release flow

1. **Update CHANGELOGs**: ask the user whether they ran the `/cl` prompt on the latest commit on `main`. If not, they must run `/cl` first to audit and update each package's `[Unreleased]` section before releasing.

2. **Local smoke test**: build an unpublished release and smoke test from outside the repo (so it can't resolve workspace files):
   ```bash
   npm run release:local -- --out /tmp/ai-local-release --force
   cd /tmp

   # Node package install smoke tests
   /tmp/ai-local-release/node/ai --help
   /tmp/ai-local-release/node/ai --version
   /tmp/ai-local-release/node/ai --list-models
   /tmp/ai-local-release/node/ai -p "Say exactly: ok"
   /tmp/ai-local-release/node/ai

   # Bun binary smoke tests
   /tmp/ai-local-release/bun/ai --help
   /tmp/ai-local-release/bun/ai --version
   /tmp/ai-local-release/bun/ai --list-models
   /tmp/ai-local-release/bun/ai -p "Say exactly: ok"
   /tmp/ai-local-release/bun/ai
   ```
   Verify both Node and Bun startup, model/account listing, interactive startup, and at least one real prompt with the intended default provider. The bare commands `/tmp/ai-local-release/node/ai` and `/tmp/ai-local-release/bun/ai` start interactive mode; run each in tmux, submit a prompt, and wait for the model reply before considering the interactive smoke test passed. Failures are release blockers unless the user explicitly accepts the risk.

3. **Run the release script**:
   ```bash
   PI_ALLOW_LOCKFILE_CHANGE=1 npm_config_min_release_age=0 npm run release:patch    # fixes + additions
   PI_ALLOW_LOCKFILE_CHANGE=1 npm_config_min_release_age=0 npm run release:minor    # breaking changes
   ```
   Use `npm_config_min_release_age=0` only for the release command. The repo's normal npm age gate can otherwise block the release lockfile refresh when the current workspace package version was published recently. Review any lockfile or shrinkwrap diffs the release creates before push.

   The release script bumps all package versions, updates changelogs, regenerates release artifacts, runs `npm run check`, commits `Release vX.Y.Z`, tags `vX.Y.Z`, adds fresh `## [Unreleased]` changelog sections, commits `Add [Unreleased] section for next cycle`, then pushes `main` and the tag. Do not rerun the release script after a tag was pushed.

4. **CI publishes npm packages**: pushing the `vX.Y.Z` tag triggers `.github/workflows/build-binaries.yml`. The `publish-npm` job uses npm trusted publishing through GitHub Actions OIDC with environment `npm-publish`; no local `npm publish`, `npm whoami`, OTP, or WebAuthn flow is required.

5. **If CI publish fails**: inspect the failed `publish-npm` job. The publish helper is idempotent and skips package versions already present on npm, so rerun the tag workflow after fixing CI or transient npm issues. Do not rerun `npm run release:patch` or `npm run release:minor` for the same version.

### 7.3 Binary distribution

`npm run build:binary` (in `packages/coding-agent/`) produces a single-file Bun-compiled `dist/pi` (this fork: `dist/ai`) binary. The binary bundles all four packages plus dependencies, so the `dist/` size is large but the install is one file. Used for `dist/pi` releases on GitHub and (in the fork) `dist/ai` for the `@simpletoolsindiaorg/ai-coding-agent` package's binary distribution.

## 8. Subagent & Extension System

### 8.0 Built-in todo tool (LLM-callable, enabled by default)

`packages/coding-agent/src/core/tools/todo.ts` exposes a `todo` tool that the main agent uses to maintain a session-scoped todo list visible to the user. The tool replaces the entire list on each call (the LLM is the source of truth; the user only observes).

Shape: `{ todos: [{ content, activeForm?, status }, ...] }` where `status` is `pending` | `in_progress` | `completed`. Constraints: at most 10 items, at most one in_progress at a time, non-empty content.

State lives in `packages/coding-agent/src/core/todo/store.ts` — a singleton `TodoStore` with a version counter and pub/sub for UI invalidation. The TUI component `packages/coding-agent/src/modes/interactive/components/todo-list.ts` subscribes and re-renders on every change, showing a checklist in the chat header.

Scope: ephemeral per-session. Cleared on `/new`, `/compact`, and explicit `clear()` (which the tool doesn't expose but the store provides). Not persisted to disk.

Why enabled by default: managing a todo list is harmless and gives the user visibility into multi-step work. The LLM is told to keep the list short (≤ 10) and use it for non-trivial tasks.

### 8.1 Built-in subagent tool (LLM-callable)

`packages/coding-agent/src/core/tools/subagent.ts` exposes a `subagent` tool that the main agent can call mid-turn when it needs specialized help. Three modes (mirroring the extension):

- **Single**: `{ agent, task }` — one subagent
- **Parallel**: `{ tasks: [{agent, task}, ...] }` — up to 8 in parallel (max 4 concurrent)
- **Chain**: `{ chain: [{agent, task}, ...] }` — sequential, `{previous}` placeholder

The tool spawns a separate `ai` process running the named agent (from `.ai/agents/` or `~/.ai/agent/agents/`), captures the JSON event stream, and returns a compressed markdown summary plus usage stats. The LLM sees only the final text by default; set `includeSteps: true` for a full tool-call transcript.

When to use: separable sub-parts, deep investigation without polluting main context, fresh look after a failed attempt. When NOT to use: simple file reads/greps, write operations (subagents are read-only), single tool-call answers.

The tool is **not enabled by default** in `defaultActiveToolNames` (`["read", "bash", "edit", "write"]`) — opt-in via settings or the SDK. This is deliberate: spawning a subprocess is expensive and the agent should think before doing it.

### 8.2 Subagent extension (this repo)

The `subagent` extension (in `packages/coding-agent/examples/extensions/subagent/`) is the example reference. It spawns a separate `ai` process per subagent, giving each its own context window. It supports three modes:

- **Single**: `{ agent, task }` — one subagent
- **Parallel**: `{ tasks: [...] }` — up to 8 tasks, 4 concurrent
- **Chain**: `{ chain: [...] }` — sequential, `{previous}` placeholder

This repo's `.ai/agents/` has three project-local subagent definitions built on this extension:

| Agent | Domain | Model (Ollama local) | Effort |
|-------|--------|----------------------|--------|
| `backend-scout` | APIs, services, middleware | `granite4.1:8b` | High (8B params) |
| `db-scout` | Schemas, migrations, ORM | `granite4.1:8b` | High (8B params) |
| `frontend-scout` | Pages, components, state | `gemma4:latest` | Medium |

The `/scout-stack` prompt fans out all three in parallel; `/scout-backend` `/scout-db` `/scout-frontend` run a single scout. The agents are tuned to short-circuit via targeted grep for trivial questions and use their full capability only for deep analysis.

### 8.2 Writing new extensions

- Place a TypeScript file in `~/.ai/agent/extensions/` (user) or `.ai/extensions/` (project)
- Or create a directory with a `package.json` that has an `"ai": { "extensions": [...] }` field
- The default export is `function (ai: ExtensionAPI) { ... }`
- Use the `ai` API to register tools, commands, providers, events, hooks, etc.
- See `packages/coding-agent/examples/extensions/` for 60+ working examples

### 8.3 Extension API surface

`ExtensionAPI` exposes (non-exhaustive):

- **Tools**: `ai.registerTool({ name, description, parameters, execute })`
- **Commands**: `ai.registerCommand(name, { description, handler })`
- **Providers**: `ai.registerProvider(name, config)`, `ai.unregisterProvider(name)`
- **Shell commands**: `ai.registerShellCommand(name, { description, handler })`
- **Events**: `ai.on(event, handler)`, `ai.sendMessage(message)`
- **Flags / shortcuts**: `ai.registerFlag(...)`, `ai.registerShortcut(...)`
- **State**: `ai.appendEntry(...)`, `ai.getSessionName()`, `ai.setSessionName(...)`
- **UI**: `ai.ui.notify(msg, level)`, `ai.ui.setTitle(text)`, `ai.ui.custom(component)`
- **Model**: `ai.setModel(model)`, `ai.getThinkingLevel()`, `ai.setThinkingLevel(level)`
- **Exec**: `ai.exec(command, options)`
- **Tools management**: `ai.getActiveTools()`, `ai.setActiveTools(names)`

### 8.4 Skills and prompt templates

- **Skills** are markdown files with `SKILL.md` filename. They provide domain knowledge to the model.
- **Prompt templates** are `.md` files invokable via `/<name>`. They support `$ARGUMENTS` and `{previous}` placeholders.
- Discovered from `~/.ai/agent/{skills,prompts}/` and `.ai/{skills,prompts}/`

## 9. Security Posture

### 9.1 Trust model

ai runs with the permissions of the user and process that launched it. There is **no built-in permission system**. The user is the source of trust.

Extensions, skills, prompt templates, and theme files are executable content. They can instruct the model to:
- Read any file the user can read
- Run any bash command
- Make network requests
- Write to any file the user can write
- Exfiltrate data

**Treat them as code, not as config.** Only install from sources you trust. Project-local `.ai/` directories in cloned repos should be reviewed before trusting.

### 9.2 Containerization

For stronger boundaries, containerize ai. Three patterns are documented in `packages/coding-agent/docs/containerization.md`:
- **OpenShell**: run the whole `ai` process in a policy-controlled sandbox
- **Gondolin extension**: keep `ai` and provider auth on the host while routing built-in tools and `!` commands into a local Linux micro-VM
- **Plain Docker**: run the whole `ai` process in a local container

### 9.3 Supply-chain hardening

Inherited from upstream, unchanged in the fork:

- Direct external dependencies are pinned to exact versions in `package.json`
- `.npmrc` sets `save-exact=true` and `min-release-age=2` (avoid same-day dep releases)
- `package-lock.json` is the dependency ground truth
- Pre-commit blocks lockfile commits unless `PI_ALLOW_LOCKFILE_CHANGE=1` is set
- `npm run check` verifies pinned direct deps, native TypeScript import compatibility, and the generated coding-agent shrinkwrap
- The published CLI package includes `packages/coding-agent/npm-shrinkwrap.json`
- Release smoke tests use `npm run release:local` to build, pack, and create isolated npm and Bun installs outside the repo before tagging
- Local release installs, documented npm installs, and `ai update --self` use `--ignore-scripts`
- CI installs with `npm ci --ignore-scripts`; a scheduled workflow runs `npm audit --omit=dev` and `npm audit signatures --omit=dev`
- Shrinkwrap generation has an explicit allowlist for dependency lifecycle scripts; new lifecycle-script deps fail checks until reviewed

### 9.4 Reporting vulnerabilities

See [SECURITY.md](SECURITY.md). For the fork: report to the fork maintainer. For issues inherited from upstream, also report upstream — fixes should land there first.
